## A. PR #332: QN extended-dialect 0xB4/0xB1 result frames (#235)

hedoric decoded the completed-weigh-in burst on the 20-byte extended dialect. The
handshake was already correct after v1.23.0; the scale simply never streams 0x10
after a full body-composition weigh-in, it sends 0xB4/0xB1 result frames that fell
through to the ignore branch.

Verified while reading the diff:

- gated on `isExtendedLongFrame`, so no other QN variant changes behaviour;
- trailing-sum checksum validated before any weight is taken;
- `extendedResultEmitted` suppresses the repeat burst;
- weight-only reading (impedance 0) passes `isComplete()` through its
  `reading.impedance === 0 -> weight > 0` branch, so a reading really does
  resolve and publish;
- `computeMetrics` routes impedance 0 to the Deurenberg fallback, which is the
  same path broadcast-only scales use. No fake BIA numbers.

Residual, non-blocking: if the burst ever started with `0xB1 03 01` before the
0xB4, the reading would resolve on the less accurate value (75.25 vs 75.20 in the
capture). The capture has 0xB4 first in both connects, and deferring 0xB1 would
risk losing the reading entirely on a unit that sends no 0xB4. Merge as authored,
record the assumption in the merge comment.

## B. QN es26m 19-byte dialect: stop forcing proto 0x00 (#75, #331)

### Evidence

- `roberfernandez` (#75) Arboleaf: `QN RAW (19B): [12 13 ff 54 0b 04 00 07 ff ...]`,
  byte[2] = 0xFF, logged as `dialect=es26m, proto=0x00`, handshake completes,
  then silence.
- `chriba2567` (#331) Arboleaf CS10E firmware 39: identical shape, identical stall,
  over an ESPHome proxy instead of native BlueZ.
- `hedoric` re-read the Renpho.txt capture attached to #84 (same es26m family):
  the vendor app drives it with proto 0xFF and needs no measurement trigger; it
  streams ordinary 0x10 frames.
- The 18-byte ES-26M was hardware-verified in 45e4d6e as REJECTING 0xff and
  working on 0x00. That one must not regress.

### Change

Split the proto decision away from the dialect decision in `src/scales/qn-scale.ts`:

- keep `EXTENDED_INFO_FRAME_LEN = 20` as the gate for `isExtendedLongFrame`
  (it gates the measurement trigger and the 0xB4/0xB1 decode from item A);
- add `PROTO_ECHO_MIN_INFO_FRAME_LEN = 19`: frames of 19 bytes or more echo
  `data[2]`, the 18-byte frame keeps 0x00;
- add a one-shot proto fallback. When the first attempt echoed a non-zero proto
  on a NON-extended long frame and no weight-bearing frame has arrived within
  `PROTO_RETRY_MS` of the 0x22 START, re-run the config + ready + start sequence
  once with proto 0x00 and log the retry.

Gating for the retry, all four required:

1. `isLongFrameVariant === true` (a long 0x12 was actually seen);
2. `isExtendedLongFrame === false` (the 20-byte dialect is proven on 0xff);
3. `seenProtocolType !== 0x00` (nothing to fall back from otherwise);
4. no 0x10 / stable / stored / result frame decoded this session.

The retry timer is cleared in the same places `fallbackTimer` and
`storedRetryTimer` are cleared, including `onSessionEnd`, so a stale timer can
never write through a dead context (the #138 failure mode).

### Tests

- 19-byte 0x12 frame with byte[2]=0xff produces config/start commands carrying
  0xff (assert on the captured write bytes, not on internal state);
- 18-byte frame still produces 0x00;
- 20-byte frame unchanged (still extended, still gets the trigger);
- retry fires once and only once after silence, and does not fire when a 0x10
  frame arrived;
- retry does not fire on the 20-byte extended dialect;
- timers cleared on `onSessionEnd`.

### Risk

Medium. It changes the handshake for every 19-byte es26m unit in the field, which
is the ES-CS20M / Elis 1 / Arboleaf family. Mitigated by the fallback: a unit that
rejects 0xff gets a second pass on 0x00 instead of a dead session. Both reporters
have offered to test.

## C. Hutbit raw impedance on the FD01 frame (#322)

RussH reported `AC 02 FD 01 <impedance u16 BE> CB <cksum>`, verified against this
file's own checksum (`FD+01+02+06+CB = 0x1D1 -> 0xD1`). Samples now:

```
User1  102.5-103.3 kg  518 ohm
User2   58.50 kg       539 ohm
User2   58.10 kg       619 ohm
```

Two users, three readings, values that move with the person rather than sitting
fixed. `FD FF` is the no-contact sentinel.

### Change in `src/scales/hutbit.ts`

- parse the FD01 frame after the existing 8-byte header and checksum gates;
- treat `data[3] === 0xff` (no contact) and an out-of-range value as "no
  impedance" and keep the weight-only path;
- accept only a plausible whole-body range (150 to 1200 ohm) so a mis-framed
  notification cannot reach `computeBiaFat`;
- remember the last stable weight so the impedance frame can be paired with it;
- adopt the existing hold-for-composition capability rather than inventing
  machinery: `completionHoldMs` plus `isFinal(reading) = reading.impedance > 0`,
  exactly the Koogeek-S1 pattern. A unit that never sends FD01 resolves
  weight-only when the window expires, so the SWAN/Lefu OEM units do not regress;
- `computeMetrics` feeds `computeBiaFat` when impedance is present, same guard
  the other adapters use;
- correct the class comment: it currently says the raw impedance "is not decoded
  here yet".

### Tests

- FD01 frame decodes 518 ohm and pairs with the preceding stable weight;
- `FD FF` sentinel yields no impedance and no crash;
- checksum failure rejected;
- out-of-range value rejected;
- `isFinal` false for the weight-only frame, true once impedance is present;
- an FD01 arriving with no preceding stable weight does not fabricate a reading.

### Risk

Low. Everything is additive behind the existing 8-byte/checksum gates, and the
hold window is the documented capability for exactly this shape of protocol.

## D. `Advert:` debug line on every transport (#322 follow-up)

RussH could not produce the `Advert:` line because only the node-ble handler emits
it (`src/ble/handler-node-ble/device-object.ts`). mqtt-proxy, esphome-proxy and
noble log nothing equivalent, which is a real diagnostic gap: adapter mis-routing
was the root cause of #317, #318 and #319, and those are exactly the reports that
arrive over a proxy.

Change: extract the formatter into a shared helper that takes the already-built
`BleDeviceInfo` (name, address, service UUIDs, characteristic UUIDs, manufacturer
data) and emit it from every handler at the point the device is accepted.
node-ble keeps its richer D-Bus specific version (address type, advertising
flags) since those fields do not exist on the other transports.

### Tests

- formatter output for a full `BleDeviceInfo`;
- formatter with empty/absent fields does not throw and says so.

### Risk

Low, debug logging only.

## E. Beurer BF788 stalls after the profile commit (#229)

petanque's 2026-08-19 full log on v1.23.0 shows: consent accepted (`[20 02 01]` on
2A9F), all four profile fields read back and written, `user profile committed
(4 characteristics, 0 written from config)`, `user-list status 0x02` on fff2, then
nothing at all for the full two-minute window, twice in a row.

What the log cannot answer: whether the 2A99 Database Change Increment write
actually happened. The code writes it only when the characteristic is present, and
the commit log line does not report it. The characteristic IS present on his scale
(`2a99 flags=[read, write, notify]`), so the write should have run, but "should"
is not evidence.

Change: log the increment write and its outcome explicitly, and fold the result
into the existing commit line so a single log line answers the question next time.
No behaviour change.
