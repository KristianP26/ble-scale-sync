# Plan: #168 BF720 BlueZ pairing agent (encrypted-link bonding)

## Problem

BF720 (unlike BF105) enforces an encrypted/bonded BLE link before its SIG User Data /
Weight / Body Composition CCCDs can be enabled. v1.17.0 added a best-effort
`device.pair()` in `ensureBonded` (`src/ble/handler-node-ble/scan.ts`), but on the
reporter's HA add-on it fails with `Authentication Failed`, because BlueZ has **no
pairing agent registered** in the container. With no agent, BlueZ cannot complete even
a Just-Works pairing, and cannot supply a passkey if the scale demands Passkey Entry.

## Evidence from the openScale HCI snoop (decoded this session)

- L2CAP CIDs in the capture: only `0x0004` (ATT). **No `0x0006` (SMP)** traffic.
- Host issued `HCI_LE_Start_Encryption` using a **stored LTK**, then `Encryption Change
  enabled=1`, twice (two connections). So the phone was **already bonded**; the capture
  reused an existing bond and shows no fresh pairing.
- Consequence: the capture proves encryption is mandatory, but cannot reveal the
  original pairing association model (Just Works vs Passkey Entry) or whether the
  4-digit PIN is the BLE passkey. The BF720 manual + openScale `bt_error_pin_format_invalid`
  string + BF105 showing a PIN on its control unit strongly suggest Passkey Entry, but
  this is unconfirmed.

## Design decision

Register a BlueZ pairing **agent** with capability `KeyboardDisplay` (the most flexible
capability — covers both Just Works and Passkey Entry initiated from either side):

- `RequestPasskey` → return the configured `beurer_pin` (covers Passkey Entry where the
  scale displays a code and we must input it).
- `RequestPinCode` → return `String(beurer_pin)` (legacy BR/EDR; harmless for LE).
- `RequestConfirmation`, `RequestAuthorization`, `AuthorizeService` → accept (Just Works
  / numeric comparison / service authorization).
- `DisplayPasskey`, `DisplayPinCode` → log only.
- `Release`, `Cancel` → log only.

Every callback logs at debug level which method BlueZ invoked + the device path, so the
reporter's retest log reveals the actual association model on real hardware (this is how
we will finally confirm Just Works vs Passkey, and whether `beurer_pin` is the passkey).

After a successful pair, set the device `Trusted=true` so future reconnects do not
re-prompt.

`beurer_pin` is reused as the BLE passkey hypothesis (the manual mentions a single
4-digit PIN). If a future capture shows the BLE passkey differs from the app consent
code, a separate `beurer_ble_passkey` option can be added later; out of scope now.

## Files

### New: `src/ble/handler-node-ble/agent.ts`

- `class BlueZPairingAgent extends Interface` implementing the `org.bluez.Agent1` methods
  above. Configured via `Interface.configureMembers` (decorators are not enabled in this
  TS config). Holds a `pinProvider: () => number | undefined` so the current `beurer_pin`
  is read at callback time (the agent is registered once but the pin can change on reload).
- `registerPairingAgent(bus, pinProvider)`:
  - idempotent (module-level `registered` flag + stored instance);
  - `bus.export(AGENT_PATH, agent)`;
  - proxy `org.bluez` `/org/bluez`, interface `org.bluez.AgentManager1`;
  - `RegisterAgent(AGENT_PATH, 'KeyboardDisplay')` (ignore `AlreadyExists`);
  - `RequestDefaultAgent(AGENT_PATH)` (best-effort, log on failure);
  - all wrapped best-effort: log a warn and continue unbonded on any failure, so
    non-bonding scales are never blocked and a missing AgentManager1 is non-fatal.
- `unregisterPairingAgent(bus)`: best-effort `UnregisterAgent` + `bus.unexport`, used from
  `resetConnection`. Clears the module flag.
- `AGENT_PATH = '/org/blescalesync/agent'`.
- Constants: capability string, agent path. Use `DBusError` from dbus-next for any
  rejection paths (none needed for the accept-all design, but `Cancel`/`Release` are void).

## Plan review (corrections applied before implementation)

1. **Pin staleness on reload.** The agent is registered once (idempotent), but the
   `beurer_pin` can change on a config hot-reload. The first closure would pin the old
   value. Fix: `BlueZPairingAgent` holds a **mutable** `pinProvider` field;
   `registerPairingAgent` updates it on **every** call (even when registration is
   short-circuited), so the latest pin is always read at callback time.
2. **No-pin passkey.** `ensureBonded`/pairing runs before `onConnected` (which throws the
   "set beurer_pin" error). If `pinProvider()` is undefined at pairing time, `RequestPasskey`
   / `RequestPinCode` must **throw `DBusError('org.bluez.Error.Rejected')`** rather than
   return `0` (a bogus passkey). BlueZ then fails the bond cleanly and `onConnected` still
   surfaces the clear pin-missing message. For Just Works the passkey callbacks never fire,
   so this does not block pin-less Just-Works bonds.
3. **Types.** `dbus-next` ships `types.d.ts` (`interface.Interface`, `configureMembers`,
   `DBusError`, `MessageBus.export/unexport/getProxyObject`). `agent.ts` imports `dbus-next`
   **statically** via a namespace import (`import * as dbusNext from 'dbus-next'`) and
   `extends dbusNext.interface.Interface`. This is safe cross-platform because
   `handler-node-ble/*` is only dynamically imported on Linux (and `scan.ts` already
   statically imports `node-ble`). Minimal `dbus.ts` change; no async-import gymnastics.
   `node-ble`'s `Bluetooth` type does **not** expose `dbus`, so `connection.ts` `getBus()`
   casts `bluetooth.dbus` to `MessageBus` (same "declare only what we use" convention as
   `helperOf`).
4. **Test reset.** The module-level `registered` flag persists across Vitest cases; export
   an internal `__resetPairingAgentStateForTests()` so idempotency and failure tests start
   clean.
5. **Prettier.** Use `npx prettier --check` on changed files (the repo `format` script
   writes, not checks).

## Post-implementation review (vs plan)

Implemented as planned, with three intentional deviations and one fix found during the
post-implementation review:

- `unregisterPairingAgent` (async, UnregisterAgent + unexport) replaced by a sync
  `forgetPairingAgent`: destroying the D-Bus connection in `resetConnection` makes BlueZ
  drop the agent automatically (owner gone), so an explicit UnregisterAgent only races the
  teardown. Cleaner and avoids using a bus that is about to close.
- `dbus.ts` was not modified: `dbus-next` ships `types.d.ts`, so `agent.ts` imports
  `MessageBus` / `interface.Interface` / `DBusError` directly and `connection.ts` casts
  `bluetooth.dbus` to `MessageBus`. Less churn than widening the local surface types.
- Found + fixed during review: two existing suites (`connect-recovery-rssi-skip.test.ts`,
  `handler-node-ble-grace.test.ts`) `vi.mock('dbus-next')` with only `Variant`. Importing
  the new agent module through the handler chain needs `interface.Interface` +
  `configureMembers` + `DBusError`, so both mocks were extended with that minimal surface.
