### A. #289 Eufy P2 Pro — extreme impedance (7,279,376 Ω), always 60% body fat
- Root cause: `src/scales/eufy-p2.ts` `parseWeightNotification` decodes impedance as
  `(data[10]<<16)|(data[9]<<8)|data[8]` (LE24). Upstream reference
  bdr99/eufylife-ble-client has this exact line **commented out** for T9148/T9149 —
  those bytes are not a usable resistance. Weight decode `((data[7]<<8)|data[6])/100`
  is correct and matches upstream. The repo shipped the guessed impedance; real hardware
  yields millions of Ω → computeBiaFat clamps to 60%.
- The existing test uses a SYNTHETIC frame (encodes 543, decodes 543) so it never
  validated the real decode.
- Fix: stop decoding impedance from this frame. `parseWeightNotification` returns
  `{ weight, impedance: 0 }`. GATT readings then flow through the same weight-only /
  BMI (Deurenberg) path the broadcast branch already uses (`isComplete` already
  returns `weight > 0` when impedance === 0; `computeMetrics` already falls back).
- Update the frame-format doc comment (bytes 8..10 are NOT usable impedance; upstream
  disabled it) and the test (drop the synthetic-impedance round-trip expectation; assert
  weight parsed, impedance 0). Keep `computeMetrics` impedance-path test that passes an
  explicit reading (still valid as a unit of the metrics pipeline).
- Reporter ask: capture raw FFF2 frames (DEBUG) alongside the eufy app's reported
  body-fat for several people, so a real impedance decode can be attempted later.

### B. #291 Hutbit — FFB2 stream reaches proxy, add-on decodes 0 frames
- Reporter (bondesen) isolated it: dedicated ESPHome proxy shows a steady
  `ESP_GATTC_NOTIFY_EVT handle=0x18` (FFB2) stream, but `HutbitAdapter.parseNotification`
  logs zero `Hutbit frame:` lines. Two hypotheses: (1) frames reach parseNotification but
  fail the length(8)/header(AC02)/checksum gate (different shape), or (2) frames dropped
  in `src/ble/handler-esphome-proxy/gatt.ts` `subscribe` on the `m.handle === handle`
  guard (discovery handle vs notify-event handle mismatch).
- No raw bytes are logged anywhere on this path, so the current logs cannot disambiguate.
- Fix (diagnostic, safe, additive — helps every esphome adapter, not just Hutbit):
  1. `gatt.ts subscribe`: in the notify listener, when `m.address === addr`: if the
     handle matches, `bleLog.debug` the handle + hex payload; if it does NOT match, a
     debug line reporting got-handle vs expected-handle (reveals a wrapper-drop).
  2. `hutbit.ts parseNotification`: add `bleLog.debug(\`Hutbit RAW (${data.length}B): ${hex}\`)`
     at the very top, before the length gate (mirrors ADE-A2 / QN).
- Reporter runs the build → raw frames settle (1) vs (2). Reporter offered a PR from their
  fork for the eventual real fix.

### C. #290 Beurer BF950 — "GATT server acquisition timed out" on Docker/node-ble
- Works on Windows/noble (OS-level pairing store), fails on the add-on. Log: connect OK,
  then `device.gatt()` times out (GATT service resolution never completes). BF950 uses
  BeurerBf720Adapter (`requiresBonding = true`).
- `ensureBonded` (scan.ts) is called only AFTER `device.gatt()` + char discovery
  (scan.ts:366). For BF720 that is fine (services resolve unbonded; only the CCCD needs
  the bond). BF950 appears to withhold service resolution until the link is encrypted, so
  `device.gatt()` hangs before ensureBonded ever runs.
- Fix (targeted, cannot regress the working BF720 path): keep the existing order, but if
  `device.gatt()` (or char discovery) times out AND `matchedAdapter.requiresBonding` AND
  the device is not yet bonded, run `ensureBonded` (which registers the BlueZ agent +
  pairs with the beurer_pin) and retry `device.gatt()` once. Normal flow where gatt()
  succeeds is untouched.
- Confidence: medium; the node-ble scan flow is delicate (#273/#1489 handling). Needs
  RudolfRendier to validate a dev build with `DEBUG=true`. Ask for the DEBUG log and
  `bluetoothctl paired-devices` output.
