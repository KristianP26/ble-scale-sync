## Work items

### A. #235 + #75 — QN AE00 gate: implement the JieLi RcspAuth response

Evidence (hedoric, 2026-08-03, two comments on #235, backed by a 2.4 MB
btsnoop with 5 complete vendor-app weigh-ins):

* Data path is `fff1` notify / `fff2` write. `ae01`/`ae02` is an auth channel
  only. Our adapter already uses fff1/fff2 and already subscribes AE02.
* Two challenge/response exchanges per session, `0x00` = challenge,
  `0x01` = response, 16-byte payloads. The one an adapter must answer is
  exchange B: scale sends `00 || challenge` on AE02, host writes
  `01 || response` to AE01.
* Transform: Bluetooth E1 (SAFER+ keyed MAC) as used by JieLi `RcspAuth`
  (`libjl_ota_auth.so`), with static constants
  * link key `06775f87918dd423005df1d8cf0c142b`
  * address constant `112233332211`
  * `response = E1(key = LinkKey, rand = challenge, addr = AddressConstant)`
* Reporter emulated the native ARM code and matched 10/10 captured pairs in
  both directions.

10 verification vectors are in the issue text (5 pairs exchange A + 5 pairs
exchange B). Both directions use the same transform, so all 10 are usable as
test vectors regardless of who generated the nonce.

Plan:

1. New module `src/scales/jieli-auth.ts` (pure, no BLE imports):
   * SAFER+ round function, key schedule, `Ar` and `Ar'` (the E1 variant where
     the round-1 input is re-added at round 3), the key-offset function, and
     `e1(key: Buffer, rand: Buffer, addr: Buffer): Buffer` returning 16 bytes.
   * Exported `jieliAuthResponse(challenge: Buffer): Buffer` that applies the
     two static constants and returns the 16-byte response body.
   * No new dependency; Node has no SAFER+ primitive and pulling one in for
     this is not worth it.
2. Verification gate before any wiring: a test file
   `tests/scales/jieli-auth.test.ts` asserting all 10 captured pairs. If the
   implementation does not reproduce 10/10, do NOT ship a guess: fall back to
   asking hedoric for the reference module they offered (comms item below) and
   leave the adapter behaviour unchanged. The Bluetooth spec's own E1 sample
   data is a useful intermediate check while debugging the primitive.
3. Wire into `src/scales/qn-scale.ts`:
   * `isAe00Challenge(data)`: `data.length === 17 && data[0] === 0x00` (restore
     the header check; the uncommitted relaxation goes away).
   * On a challenge: compute the response and `writeAe01([0x01, ...response])`.
     Keep the existing best-effort write helper, which already swallows a
     missing AE01.
   * Keep answering every challenge in a session, not just the first: the
     capture shows the scale challenges once, but a re-challenge after a
     re-subscribe is plausible and answering is idempotent. Keep the
     once-per-session log line (`ae00ChallengeSeen`) so the log does not
     repeat, but decouple it from the response itself.
   * Rewrite the `noteAe00Challenge` doc comment and log text: it currently
     states that no response is sent and asks for a capture, which becomes
     false and would confuse #75 readers.
   * Leave exchange A (host-initiated challenge) unimplemented. The capture
     shows the scale does not require it before streaming, and inventing a
     nonce we then have to validate the answer to adds a failure mode for no
     gain. Note this explicitly in the module comment.
4. Adapter tests in `tests/scales/qn-scale.test.ts`: feeding the #75 challenge
   frame on AE02 produces exactly one AE01 write of `01 || <expected>`, and a
   non-challenge AE02 frame still falls through to `parseNotification`.

Risk: the scales in #235 and #75 are different units (GE CS 10 G, Renpho Elis
1) and only the GE was captured. #75's challenge frames have the same shape
(17 bytes, `0x00` header, one per session, no QN checksum), so the same gate is
the best hypothesis, but the Elis 1 may use a different key. Both reporters
must retest; the comment must say that plainly rather than promising a fix.

### B. #317 — Renpho ES-26BB claimed by R-MSC04 on the mqtt-proxy autonomous path

Root cause (confirmed in source, not inferred from the log alone):
`handler-mqtt-proxy/watcher.ts` builds `toBleDeviceInfo({... name: '' ...})` for
an autonomous connect, so no descriptor match can fire on a name. Both Renpho
adapters match by exact name only, so `resolveAdapter` returns undefined and the
code falls through to a priority-ordered `charNotifyUuid` scan. R-MSC04
(priority 235) and ES-26BB (priority 230) both declare notify `0x2A10`, so
R-MSC04 wins, then `onConnected` subscribes `0x2A12`, which this device does not
expose, and the session dies with
`Characteristic 00002a12... not found`. Before v1.21.0 the R-MSC04 adapter did
not exist, which is exactly the regression window the reporter observed.

Reporter's char list confirms it: `2a10` and `2a11` present, `2a12` absent.

Fix: the notify-char fallback must not select an adapter whose other required
characteristics are missing. Filter candidates by requiring every declared
`characteristics[]` binding (multi-char adapters) and `charWriteUuid` (single
-char adapters) to be present in the discovered set, then apply the existing
priority order. R-MSC04 requires 2a10 + 2a11 + 2a12, drops out, ES-26BB matches
2a10 + 2a11 and wins.

Keep it a filter, not a hard requirement: if NO candidate satisfies the full
set, fall back to today's notify-only behaviour so nothing that works today can
stop working. Log which adapters were rejected and why at debug.

Tests: `tests/ble/handler-mqtt-proxy.test.ts` — the reporter's exact 16-char
list resolves to ES-26BB, and a char set containing 2a10 + 2a11 + 2a12 still
resolves to R-MSC04.

### C. #319 — mqtt-proxy host-initiated GATT never re-resolves after discovery

Reporter (flamingspaz) located this precisely and it checks out:
`handleGattReading()` receives the advertisement-time adapter and passes it to
`waitForRawReading()` without re-resolving against `connected.charMap`. The
node-ble path (#177), the esphome path (#251) and this handler's own autonomous
path all re-resolve; the host-initiated path was missed. A Eufy A1 (T9120)
exposing fff1 + fff4 and no fff2 is driven by Inlife or QN and dies on the
missing write characteristic.

Fix:

1. In `handleGattReading()`, after `mqttGattConnect()` resolves, re-resolve with
   `characteristicUuids` populated from `connected.charMap.keys()`, fall back to
   the advertisement-time adapter when nothing matches, and log the switch at
   info when the name changes.
2. `src/ble/shared.ts`: include the adapter name in the
   `Required characteristics not found` error. This failure almost always means
   the wrong adapter was selected and the message currently omits the one fact
   that says so.

Deliberately NOT doing in this pass: the reporter's "remaining gap", a
structural `fff4 && !fff2` exclusion inside `QnScaleAdapter`'s nameless
fallback. It is the right observation, but QN is the most widely deployed
adapter in the registry, the nameless fallback is what rescues proxy transports
that deliver no name, and there is no report of a nameless fff4-without-fff2
device today. Item F gives affected users an immediate escape hatch, and this
stays open for a targeted change once someone reports it. Say so in the reply
rather than silently skipping it.

Tests: regression test in `tests/ble/handler-mqtt-proxy.test.ts` reproducing the
reporter's char list (fff1 + fff4, no fff2) and asserting the adapter driving
the read is `1byone (Eufy)`.

### D. #318 — SWAN with a 6-byte 0x02AC payload matches MGB instead of Hutbit

`isHutbitOemAdvert()` requires a 7-byte manufacturer payload whose last byte is
a 0x00/0x01 status flag. The reporter's advert carries `12a291ecb303`, six
bytes, which is exactly their MAC `03:B3:EC:91:A2:12` reversed with no status
byte. The predicate returns false, so Hutbit (priority 35) declines and MGB
(priority 30) takes it on `startsWith('swan')` and then never completes,
because the frames are Hutbit AC02 8-byte frames, which the reporter decoded
and which the MGB parser rejects.

Fix: accept a 6-byte payload (MAC only) as well as the 7-byte (MAC + status)
form, still gated behind both FFB0 and D618 in the advertised services. Update
the module doc to record both observed shapes and which capture each came from.

Symmetry requirement: `RobiS9Adapter.matches()` bows out to this same
predicate, so widening it also widens Robi's bow-out. That is the documented
intent of the shared predicate (an asymmetric pair strands the device with
MGB). Verify the Robi test suite still passes and that no Robi advert in the
tests carries a 6-byte 0x02AC payload alongside FFB0 + D618.

Tests: `tests/scales/hutbit.test.ts` — the reporter's exact advert resolves to
Hutbit; the 7-byte form still resolves to Hutbit; a 6-byte 0x02AC payload
WITHOUT D618 still does not.

### E. #289 — Eufy P2 Pro: impedance is at bytes [4..5], /10

New evidence from Langybangy (2026-08-08), six sessions with the vendor app's
body-fat value recorded next to each:

| session | final frame | app body fat |
|---|---|---|
| socks on, 88.00 kg | `cf 0e 00 cf 00 00 60 22 00 00 00 00 00 00 00 8d` | none |
| socks off, 88.00 kg | `cf 0e 00 cf 5c 12 60 22 11 13 f1 00 00 00 00 30` | 30.4 % |
| 20 kg dumbbell | `cf 0e 00 cf 00 00 d0 07 00 00 00 00 00 00 00 18` | none |
| person 2, barefoot, 68.45 kg | `cf 0e 00 cf 72 1a bd 1a 06 05 62 00 00 00 00 61` | 42.4 % |
| person 2, shoes, 68.70 kg | `cf 0e 00 cf 00 00 d6 1a 00 00 00 00 00 00 00 03` | none |

Bytes [4..5] and [8..10] are zero in every session where the app reported no
body fat, and non-zero in exactly the two sessions where it did. That is
structural evidence the previous three-sample value-ranking analysis could not
see, and it overturns the v1.21.1 conclusion that [4..5] is not impedance. The
values as LE/10 are 470 Ω (30.4 %) and 677 Ω (42.4 %): plausible BIA magnitudes,
ordered correctly against body fat, and feeding them through `computeBiaFat`
gives 33.8 % and about 44-46 % (person 2's height/age/sex are unknown), a
consistent overshoot of 2-4 pp against the vendor app rather than the
nonsensical 60 % clamp the [8..10] interpretation produced.

Verified: length byte and the XOR over [2..14] check out on both BIA frames and
on the zero frames, so the integrity check does not reject them.

Fix in `src/scales/eufy-p2.ts`:

1. `parseWeightNotification` returns `impedance = raw/10` when the LE u16 at
   [4..5] is non-zero AND the frame passes `frameIntegrityProblems`, else 0.
2. Range gate: accept 100-1500 Ω, otherwise treat as 0 and log at debug. A bad
   value here is worse than none because `computeBiaFat` clamps silently to
   60 %, which is what made the original #289 report look like a broken scale.
3. Rewrite the block comment: it currently states [4..5] is actively disfavoured
   and impedance is undecodable. Record the new evidence, the two vectors, and
   that [8..10] stays undecoded.
4. Broadcast path stays weight-only: no advertisement sample carries these
   bytes.
5. The uncommitted blanket "reject frames with integrity problems" edit does not
   ship as-is. Weight keeps its current tolerance; integrity failure only
   suppresses the impedance, so no frame that yields a weight today can stop
   yielding one.

Tests: `tests/scales/eufy-p2.test.ts` — both real BIA frames produce the
expected impedance, all four zero-BIA frames produce 0, an out-of-range value
produces 0 with the weight intact, and an XOR-corrupted BIA frame produces the
weight with impedance 0.

Open question for the reporter (does not block shipping): person 2's height,
age and sex, so the second vector can be checked quantitatively rather than
against a guessed profile.

### F. Adapter override in config (`ble.force_adapter`)

Requested independently in #318 and #235, and named as the missing escape hatch
in #319. Every one of items B, C and D is the same failure class: a device is
claimed by the wrong adapter and the user has no way to say otherwise while
waiting for a release.

Design:

* Config: `ble.force_adapter: <string>`, matched case-insensitively against
  `adapter.name`. Validated at load: an unknown value fails validation with the
  full list of adapter names, because silently ignoring a typo here reproduces
  exactly the confusion the option exists to remove.
* Implementation: a module-level override in `src/scales/resolve.ts`
  (`setForcedAdapter(name | undefined)`), consulted at the top of
  `resolveAdapter`. Every handler already funnels through `resolveAdapter`
  (node-ble post-discovery, both proxies, both proxy sub-paths), so one place
  covers all transports, including the notify-char fallback path in item B,
  which must also honour it.
* The override returns the named adapter regardless of `matches()`. That is the
  point: the user is overruling detection. Log at info once per session.
* Broadcast-only paths: the override applies there too; an adapter that cannot
  parse the advertisement simply yields nothing, which is the user's choice.
* Docs: `docs/configuration.md` (or wherever `ble.*` lives) plus
  `config.yaml.example`, with a short "only use this if auto-detection picks the
  wrong adapter, and please file an issue so the matcher can be fixed" note.

Tests: unknown name fails schema validation; a set override wins over a
higher-priority matching adapter; clearing it restores normal resolution.
